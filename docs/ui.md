# UI

Layout rules for the web app that the code alone does not make obvious. The general rules (one scroller, overlays, touch targets, i18n) live in [AGENTS.md](../AGENTS.md); this file records measured values.

## Shell rules

The template's four shell rules (FlyCockpit/template, `patterns/design-system.md` § Shell rules), as this app applies them, in both themes and at every width. `pnpm policy:checks` enforces what a static check can (rules G8 and G9 in `scripts/check-web-conventions.ts`), `apps/web/src/components/public-shell.test.tsx` and `apps/web/src/lib/theme-contrast.test.ts` pin the markup and the tokens, and `pnpm check:layout --url <dev server>` measures the geometry in a browser (`pnpm dev:docker <port>` first; pass `--state <file>` with a saved signed-in admin session to add the admin page and the toast; it needs the global `agent-browser` CLI and stays out of CI). Before measuring a page it waits until `<main>` shows no skeleton or `aria-busy` region and stops growing (8 s at most, else it reports the page as still loading or still changing); its agent-browser session is `check-layout-<pid>`, behind `BROWSER_CHECK_SESSION_PREFIX` like the other browser checks (§ Browser checks).

1. **The footer sits at the bottom of a short page.** The public shell (`apps/web/src/components/public-shell.tsx`, used by the `_public` layout and the 404) owns the one public footer (`components/public-footer.tsx`; with analytics it carries Cookie preferences). Inside `<main>`, the content is one `flex min-h-full flex-col` column: the routed page grows (`flex-1`) and the footer comes last. On a short page the footer's bottom is the scroller's bottom; on a long page it follows the content. No `position: fixed` footer, no `min-h-svh` layout, no second scroller, and no site `<footer>` in a route file: footer content goes into `PublicFooter`. A footer that belongs to an `<article>`, `<section>` or another sectioning element stays inside it. The app shell (`_app`) has no footer: phones get the BottomNav, and Cookie preferences (with analytics) sits in Settings. The standalone device/OAuth pages have none either.
2. **Full-bleed dividers span their column.** The header's `<hr>`, the footer's `border-t` and the `AdminSetupBanner` above the frame reach from 0 to the viewport's right edge at every width. Rules inside the app shell's `<main>` (the admin section nav's `border-b`, `TwoFactorNudge`) reach from `<main>`'s left edge, which is the viewport's below `md:` and the sidebar's end from `md:` up (240px expanded, 64px collapsed), to the viewport's right edge. On a page that scrolls, rules inside `<main>` meet its visible scrollbar, which sits at that edge, as on any scrolling page. That is why no page scroller (`<main>` in the app and public shells and on the standalone pages) reserves a scrollbar gutter: with classic scrollbars (Windows, Linux) a stable gutter is an empty 15px strip that every rule inside the scroller stops short of, even when nothing scrolls. The cost is that centred content moves by half a scrollbar when a page grows past the viewport on those platforms; overlays don't cause it, because they lock the document, not `<main>`. Nested panes may still reserve a gutter.
3. **No surface ignores the theme.** The theme is the stored choice, else the OS, applied as the `.dark` class before first paint (`packages/config/src/theme-init.ts`). Every surface (toasts, banners, the cookie banner, popovers, menus) uses the tokens in `packages/ui/src/styles/globals.css` and `dark:` variants, never a `prefers-color-scheme` query or a literal colour; a new colour becomes a token there. A deliberate fixed colour (a QR code that must stay dark on white to scan) carries a `theme-exempt: <reason>` comment on the line above it, on its line, or inside the flagged `className`/`style` value; G9 skips that one finding, nothing else. A CSS `url(#id)` reference is not a colour. Toasts are a popover surface: `globals.css` fills sileo's pill with `--popover`, writes the title in `--popover-foreground` and maps sileo's state colours to `--state-*`, `--destructive` and `--primary`, and the Toaster (`packages/ui/src/components/sileo.tsx`) gets no `theme` prop (sileo's themes invert the page). Text and state colours reach 4.5:1 on the surface they sit on in both themes.
4. **Every route renders inside a shell, the 404 included.** An unknown URL matches no layout, so `$lang`'s `notFoundComponent` (`PublicNotFoundPage`) wraps the not-found body (`NotFoundState`) in the public shell: header with language and theme controls, footer, scroller. Layouts that keep an unknown sub-path inside the app shell set their own `notFoundComponent`: Settings (under its "Settings" heading) and a KB (`/kbs/<id>/…`). The router's `defaultNotFoundComponent` stays the body alone. A `notFound()` thrown by a route with no such layout above it lands on the public 404; that includes the admin gate, so a hidden `/admin` looks exactly like a missing page. Fixed chrome follows the shell it belongs to: the cookie banner (only with analytics) reserves room for the BottomNav only while one is mounted (`data-bottom-nav`).

The template's two rules apply here too. Boxes share the text line inside pages, cards and forms. A miss is fixed in the container (its padding, `inset`, `px-*` on a track, or the shared close-button placement), never with a one-off margin on one item.

So do the template's five rules from the apps' passes:

- **An edge text item puts its label on the box's edge.** When a text link or button is the first or last item on a line and its box is wider than its label (a 44px minimum box around a short label), start-align the label (`justify-start`) for a leading item, end-align it for a trailing one. Centring is for items in centred bars, such as BottomNav, and for icon buttons.
- **Table text sits on its container's text line.** The first and last cells drop their outer padding (or take the container's inset, e.g. `first:pl-0 last:pr-0`). Inner cell padding separates columns; it must not indent the first column from the heading above the table.
- **Overriding a Button's padding: override every breakpoint.** This app's Button sizes have one padding at every width today; the template's carry responsive paddings (`px-3 md:px-2.5`). If a size gains one, remember that tailwind-merge treats `px-*` and `md:px-*` as separate groups, so `className="px-2"` would leave `md:px-2.5` in force at `md:`. Write `px-2 md:px-2`.
- **A control flush with a clipping edge draws its focus ring inside its box** (`focus-visible:ring-inset focus-visible:ring-offset-0`). Button's default ring is drawn outside the box after an offset, and the viewport or an `overflow-*-hidden` ancestor cuts it off.
- **Frame bands keep the frame line.** Banners above the page (`AdminSetupBanner`, `TwoFactorNudge`) and the header sit 16px inside the frame. A banner's content stops at the widest page column (§ Viewport scale), so on a screen wider than that column it lines up with the widest page, not with the frame; it is never re-aligned to a narrower page container below it. The header keeps the frame line at every width.

## Viewport scale

The app follows the template's viewport scale (FlyCockpit/template, `patterns/design-system.md` § Viewport scale): it grows with the screen above 1920 CSS px, so a 4K monitor at 100 % OS scaling shows the same layout as a 1080p one instead of a small island in the middle. Phones, laptops and 1080p screens are unchanged.

1. **One root rule scales everything.** `html` in `packages/ui/src/styles/globals.css` sets `font-size: clamp(100%, calc(100% + (max(100vw, 100vh) - 1920px) / 240), 150%)`: the browser default (so a user's own default font size is respected) up to a 1920 CSS px long side, then 1px more per 240px, to 150 % at 3840. The long side makes a portrait 2160×3840 screen scale like a landscape 3840×2160 one; 4K at 200 % OS scaling is 1920 CSS px, so it is unchanged. Media queries use the browser default, so breakpoints don't move, and browser zoom still enlarges. `apps/web/src/lib/viewport-scale.test.ts` pins the rule.
2. **Sizes are rem, not px.** Type, control heights, padding, page widths, dialogs and cards use Tailwind's rem scale, so they follow rule 1. px stays for hairlines and borders, shadows, radii and touch-target floors (`min-h-[44px]` is a minimum, not a size).
3. **Text is at least 12px** (`text-xs`) at every width, labels and badges included; no `text-[10px]`. A BottomNav label that doesn't fit truncates. `pnpm policy:checks` (rule G10 in `scripts/check-web-conventions.ts`) rejects a px font size in a class (`text-[13px]`) and a rem or em one below 0.75.
4. **Pages use the width tiers.** `PageShell`'s `narrow`, `default` and `wide` (`apps/web/src/components/page-shell.tsx`) are rem, so they scale with rule 1. The `full` tier (`max-w-none`, same `px-4` edge line) is the full-width container for a page that should use the whole screen: the KB document editor (Markdown and preview side by side, `kbs/$kbId.tsx`). Reading a document keeps `default`.
5. **Full-bleed banners keep their content in the page column.** The background and border span the window; the content goes in `PAGE_COLUMN_CLASS` (`page-shell.tsx`, the `wide` tier), so the message and its action sit together instead of 3000px apart at 4K.
6. **Long copy gets `max-w-prose`**: descriptions, help text, policy explanations. `PageHeader`'s description carries it already.
7. **Card grids follow their column.** The KB list (`KB_GRID_CLASS` in `lib/kb-grid.ts`, shared with its skeletons) fits as many 15rem columns as the list's width holds (three in the default page column), so the sidebar counts and a 4K screen gets the same grid, scaled.

## Cookie banner clearance

**The banner appears only when analytics is configured; strictly necessary cookies need no consent.** The app ships no analytics: `ANALYTICS_PROVIDER` in `apps/web/src/lib/analytics.ts` is `null`, so there is no banner, no Cookie preferences (public footer, Settings), no reserved space, and the gate loads nothing. That constant is the one switch: setting a provider (`{ load() { … }, disable() { … } }`) turns the banner, the gate and Cookie preferences on together, and `apps/web/src/lib/analytics.test.ts` fails a provider whose `load` or `disable` is empty. `components/consent/consent-off.test.tsx` pins the default; the other consent tests run with the switch on.

With analytics on, the first-visit cookie banner (`ConsentBanner`) is fixed to the bottom of the viewport but never covers the page, and never shortens the shell. While it shows, it publishes its height as `--consent-inset` on `<html>` (`apps/web/src/components/consent/consent-inset.ts`), and `apps/web/src/index.css` turns that into `--consent-clearance`. The shell frames are never padded for it, so the header and the sidebar always reach the bottom of the viewport (padding the frame once cut the dashboard's sidebar ~150px short). Instead each page scroller pads its bottom by the part its frame does not already reserve, so every line scrolls into view above the banner (0 without a banner):
- the app shell's frame reserves only the BottomNav (`pb-[calc(3.5rem_+_var(--safe-area-bottom))] md:pb-0`, with the software keyboard closed), and its `<main>` pads the rest (`pb-[max(0px,calc(var(--consent-clearance)_-_3.5rem_-_var(--safe-area-bottom)))]`; `pb-(--consent-clearance)` with the keyboard open and from `md:` up);
- the public shell's frame reserves the safe-area inset, and its `<main>` pads `max(0px, clearance − safe area)`;
- the standalone device/OAuth pages are their own scrollers and pad by the larger of the clearance and the safe-area inset.

`consent-clearance-shells.test.tsx` pins the classes; `pnpm check:layout`'s banner-reserve probe measures the geometry, the dashboard's sidebar included. The shells are `h-svh` and do not shrink for the keyboard, so the clearance is the whole banner height (the template subtracts `--keyboard-inset` because its shells do shrink).

Below `sm:` the banner is one short line (`consent:banner.short`) over two side-by-side buttons (`grid grid-cols-2`, each `touch`, 44px tall), about 92px above the BottomNav at 320px; the title and full message return from `sm:` up, and the section's `aria-label` carries the title at every width. The auth card (`AuthCard`) is flat on phones (no surface, ring or inner padding) and starts just under the header instead of being centred in `80vh`; on the login page "Forgot password?" sits in the Password label's row there and the sign-up link uses half the gap above it, so at 320×568 the sign-up link stays visible above a first visit's banner.

## Layer scale

The app keeps the template's layer scale (`patterns/design-system.md` in the template repo). The banner, the BottomNav and every portal sit on the root stacking context, so these numbers compete directly. That holds only while none of them has an ancestor that opens its own stacking context (`isolate`, a `z-*` on a positioned element, `transform`, `filter`, `backdrop-filter`, `opacity` below 1, `will-change`, `contain`), so fixed chrome mounts at the shell or root level. A portaled popup competes through its outermost part (Positioner, Backdrop/Overlay, Viewport):

| Layer | Who |
|---|---|
| `z-10`, `z-20` (and `-z-1`) | Inside a component (Select's scroll arrows, a focused toggle); never used to beat app chrome |
| `z-30` | Sticky page chrome (the admin section header) |
| `z-40` | Non-modal fixed chrome over the page: the cookie banner. Below every overlay, so an open menu, select, popover, combobox, dialog, sheet, drawer or toast is never covered (a row-actions menu opened near the bottom of a list lands where the banner floats); below the BottomNav, which paints over the banner's bottom padding |
| `z-50` | The overlay layer: the `packages/ui` portals (dropdown menu, select, popover, dialog, alert dialog, sheet, drawer), the sileo toast viewport, the mobile BottomNav and the focused skip link |

Nothing goes above `z-50`. Utilities use only the steps above (`-z-1`, `z-10`, `z-20`, `z-30`, `z-40`, `z-50`): no arbitrary `z-[…]` / `z-(…)` values and no other numbers. Every overlay root carries an unconditional `z-50` (a responsive-only `md:z-50` leaves phones without a layer). A new banner, tray or floating button is `z-40` or lower and reserves its own space through the page scroller's bottom padding, never the shell frame, as the banner does with `--consent-inset`.

What checks it:

- `apps/web/src/components/consent/consent-layers.test.tsx` is the safety net. It renders the banner and checks its layer against every portaled overlay in `packages/ui/src` (read from the components, so a new overlay is covered), the sileo toast viewport and the BottomNav, and that no overlay is lowered below `z-50` through the `className` it is given (in app code or a shared wrapper such as `CommandDialog`).
- `pnpm policy:checks` is a line grep for the obvious cases: an off-scale `z-…` utility in `apps/web/src` or `packages/ui/src` (markup, class strings, `@apply`).
- Neither catches: custom CSS classes and stylesheets (`.my-sheet { z-index: 30 }`, a `[data-slot=…]` rule, however its selector is spaced, nested `@media` blocks), CSS `z-index` declarations and inline `style` / `zIndex`, class names built at runtime (`` `z-${n}` ``) or held in a constant, layers set through pseudo-element or descendant variants (`before:`, `*:`, `[&…]:`, which the test skips), and an ancestor that opens its own stacking context. Those are review items; real hit-testing needs a browser.

## Sign-up modes

The public `appConfig` (`packages/api/src/routers/index.ts`) says how a visitor gets an account. `signupMode()` (`apps/web/src/lib/signup-mode.ts`) turns it into one value, and the landing page, sign-in and `/signup` all branch on it, so no page hides the way in or bounces silently. The test server runs `closed` (`SIGNUP_ENABLED=false`): accounts come from admin and member invitations.

| Mode | Config | Landing | Sign-in | `/signup` |
| --- | --- | --- | --- | --- |
| `open` | `signupEnabled` | Create account + Sign in | "Need an account? Sign Up" link | Create-account form |
| `bootstrap` | `adminBootstrapSignupEnabled` (sign-up closed and no administrator yet; in production only `ADMIN_EMAIL` can sign up) | "Set up this server" (primary) and Sign in (the visitor is almost certainly the operator) | The "Setting up this server?" link | "Set up this server" form, plus the invite-only line for everyone else |
| `closed` | neither | Sign in + the invite-only line | The invite-only line instead of a link | "This server is invite-only" with a Sign In button; no redirect |
| `sso` | `forceSso` | Sign in | SSO-only state | `beforeLoad` redirects to sign-in |

- `adminBootstrapSignupEnabled` clears once the administrator exists (`isAdminBootstrapSignupEnabled`, `packages/auth/src/bootstrap.ts`); until then the bootstrap copy also tells everyone else the server is invite-only. A sign-up the server refuses in this mode gets one message under the email field that is true for every address; it never says whether the address is an admin or already registered (`packages/auth/src/signup-response.ts`).
- The landing page reads the mode with a client `useQuery`, which does not fetch during SSR: every anonymous render shows a neutral Sign in and the mode-specific buttons appear once `appConfig` answers. A visitor with a session cookie never sees it: they are forwarded to the signed-in home (§ The signed-in home). The public header shows Open app or Sign In from the session hint (§ Public header session hint).
- First-run copy is neutral: sign-in is titled "Sign In", and the signed-in home is titled "Knowledge bases", with no "Welcome back". Nothing in the session tells a first sign-in from a return visit (the account exists before its email is verified).
- Every 2FA step has a Cancel. On sign-in it resets the whole challenge back to the form; in the required-2FA setup and in Settings → Security it goes back to the first step and drops the typed password, the code and the unconfirmed secret (`useTwoFactorEnrollment`). A request still in flight from the cancelled attempt is ignored when it answers, but the next Continue waits (loading) for it to settle before sending its own: Better-Auth's enable replaces an unverified secret, so two at once could leave the shown QR code and backup codes invalid. The SSO passwordless hint shows only when `appConfig.ssoEnabled` is true.
- New-password fields (sign-up, reset/invite/setup link, change password) show "At least 12 characters." as their description from the start and validate with `newPasswordSchema()` (`apps/web/src/lib/password-policy.ts`), which reads the numbers Better-Auth enforces (`@knowledge-base/auth/password-policy`).
- `/signup`, forgot-password and reset-password read `appConfig` in `beforeLoad` through `ensureRouteQuery` (`apps/web/src/lib/route-query.ts`) with `orpc.appConfig.call()`, never a bare `ensureQueryData(orpc.appConfig.queryOptions())`. The header's UserMenu observes the same query. When the last observer unmounts mid-fetch (a pending shell swapping for the real one), TanStack Query cancels a fetch whose `queryFn` read the abort signal, and the route would fail into "This page didn't load". `.call()` never takes the signal, and a joined fetch that is cancelled is retried. Any other awaited route read of a query that components observe uses the same helper.

## Server errors on a field

When the server's answer is about one field (wrong password, address already registered, wrong 2FA code), it goes under that field, not only in a toast. A toast is for outcomes that are not about a field: network failure, rate limit, "couldn't save".

- In a TanStack Form, call `setServerFieldError(form, "password", message)` (`apps/web/src/lib/form-server-error.ts`). `TextField` renders it with `aria-invalid`, `aria-describedby` and `role="alert"`, and it clears when the user edits that field. Do not write `meta.errors` directly: TanStack Form derives it from `errorMap`, so the write does not stick.
- For an input kept in local state (a 2FA code, the password that starts 2FA setup), use `PlainField` / `OneTimeCodeField` (`apps/web/src/components/auth/plain-field.tsx`) and pass the message as `error`.
- Put focus back on the field after the error, and select its text when the user will retype it.
- Only the answer that is really about the field goes there: a wrong email or password (`isCredentialRejection`: the `INVALID_EMAIL_OR_PASSWORD` code only, since Better-Auth also answers 401 `FAILED_TO_CREATE_SESSION` after correct credentials), a wrong or expired 2FA, emailed or backup code (`isCodeRejection`, both in `apps/web/src/utils/friendly-error.ts`). A rate limit, a lockout or a server or network failure is a toast through `friendly(err)` with its generic fallback (a request that rejects instead of answering, e.g. offline or server unreachable, is caught and toasted the same way, at sign-in, sign-up and "email me a code"), never the "code didn't work" or "email or password doesn't match" copy, and the same values (the typed code too) can be sent again.
- When one answer covers two fields (a wrong email *or* password, shown under the password), editing either one clears it: the sign-in email field's `listeners.onChange` calls `clearServerFieldError(form, "password")`.
- "Verify your email before signing in" is an inline `role="alert"` notice under the email field with a "Send a new link" link, not a field error, because the same credentials must work once the link is clicked.

## Offline

Offline is a state, not an error: say so, say what happens next, and never leave a spinner running with no explanation.

- **The band.** The app and public shells render `OfflineBand` (`apps/web/src/components/offline-band.tsx`) in their top row, after the header (and, in the app shell, the setup banner), outside `<main>`. It takes its own height, so it never covers the page, the BottomNav or the cookie banner. It shows "You're offline. Changes you make won't be saved until you reconnect." while `navigator.onLine` is false, then "Back online." for 4 seconds. Its `role="status"` region stays mounted while empty, so each message is announced once; tokens only, and its fade is `motion-safe:` only. Don't add a second offline banner in a route.
- **One classifier.** `networkFailureKind()` (`apps/web/src/lib/network-failure.ts`) returns `offline`, `unreachable` (online, but the fetch failed) or `null`. `friendly()` maps the first two to "You're offline. Check your connection and try again." and "Couldn't reach the server. Check your connection and try again."
- **Route errors.** `ErrorState` shows "You're offline. This page will load when you reconnect." while offline and retries by itself when the network status turns back online (`useRetryOnReconnect` → `router.invalidate()`, which also reloads a failed route chunk; the hook follows the status value, not an `online` listener of its own, which the status store's re-render removed mid-dispatch); an online fetch failure shows "Couldn't reach the server". Stale-build recovery never reloads while offline (it would land on the browser's offline page), and offline it also marks TanStack's own reload-on-missing-module slot (`suppressRouterReload` in `apps/web/src/lib/stale-build-recovery.ts`), so the failed route chunk reaches `ErrorState`.
- **Queries** keep `networkMode: "online"`: offline they pause and refetch on reconnect. `QueryBoundary` shows the offline copy for a paused first load and for any error while offline; its `query.fetchStatus` is required, so a hand-built `query` prop passes it too. The global query error toast stays quiet for offline failures.
- **Mutations fail fast by default.** `installOfflineMutationPolicy()` (`apps/web/src/lib/offline-mutations.ts`, installed in `router.tsx`) runs mutations with `networkMode: "always"`, so offline the request fails at once with the offline toast, the button stops spinning and Cancel works again. Don't set `networkMode` per call.
- **Dialogs that show a mutation's error inline** map network failures through `friendly()` before their own copy, so offline says "You're offline…", not "Couldn't create…" (`createErrorText` in `components/kb/kb-list.tsx`). The Create token and Create API key pages (`pat-create.tsx`, `api-key-create.tsx`) don't send at all while the browser is offline, and say "You're offline…" inline. Nothing can have been created, so they never reach the "could not confirm whether it was created" state, which stays for a send that failed after it left.
- **Opt-in queue.** A write that is safe to replay sets `meta: { offline: "queue" }`. It pauses offline; the user is told once "You're offline. This change will be sent when you reconnect. Keep this tab open." and again when it lands. Paused mutations live in memory only. A call site that renders its own waiting state from `isPaused` adds `offlineNotice: "inline"`, so the policy shows no toast (one notice, not two).
- **The document editor queues.** Its document create and update and its upload mutations (`useKbEditor` in `apps/web/src/hooks/use-kb-editor.ts`) use `{ offline: "queue", offlineNotice: "inline" }`: every write carries its idempotency key and base revision, so a replay is safe, and the editor shows "You're offline. The change will be sent when you reconnect." under the editor. Its document delete queues too, but with the app's own queued and sent toasts (`{ offline: "queue" }`), because it also runs from the read view, which has no editor notice. Nothing else in the app queues; other deletes, permissions, credentials and sharing fail fast.

## Query cache follows identity

The TanStack Query cache, Zustand stores, module state and every in-flight request callback belong to one identity: the one the document was used by. `apps/web/src/lib/document-identity.ts` keeps that identity at module scope for the whole life of the document (never in a component, which a public page, a standalone page or an error reset would unmount and make forget). When a confirmed identity differs from it, the document is replaced with a full load. A page load is asynchronous, so every replacement first quarantines the document synchronously: the page is hidden (`display: none !important` on the root, which no descendant can undo) and the QueryClient sealed (emptied, and anything a late callback adds is removed again), so nothing of the previous identity stays on screen while the new page loads. Query keys therefore don't name the viewer, and no query needs `gcTime: 0` for privacy.

| Transition | What happens |
|---|---|
| Explicit sign-out (the account menu, `user-menu-content.tsx`) | `signOutAndLeave()` (`apps/web/src/lib/explicit-sign-out.ts`): marks the sign-out, then on success `leaveDocument()` to login, a fresh document with an empty cache. A failure (returned or thrown) undoes the mark and toasts; add any new sign-out button through it. |
| Signed out elsewhere (another tab, expiry, revocation) | The document reloads in place; the guards send the visitor to login. |
| Another account (same tab or another tab) | The document reloads in place; the guards admit the new account and its queries load fresh. |
| Anonymous → signed in | Nothing: an anonymous cache holds only public data, so password sign-in keeps its client-side navigate. |
| `pending` / `error` | Never acted on: a flaky session check must not reload a signed-in page. |

While a guard is still checking, the app shell's pending state (`_app/route.tsx` `AppShellPending`) names no account: it renders under `SessionUnconfirmed` (`apps/web/src/lib/session-unconfirmed.ts`), so `useAuthSession()` reports `pending` there and the account menu, nav and banners show their skeletons, never the session Better Auth's atom may still hold from before a switch made in another tab.

The same holds after another tab announced a change (or a request got a 401) while no watcher was mounted to check it: `useAuthSession()` reports `pending` everywhere until a fresh check confirms this document's identity or replaces the document: a guard's server answer, or a refetch the watcher itself starts when it mounts (retried on focus, visibility and reconnect while unverified). An answer asked for before a newer invalidation never counts, so a guard error or an unguarded page never shows the stale account either, and a guard whose probe was overtaken by an announcement asks again before admitting anything (`resolveRouteSession`, at most 3 probes, then its retryable error state, whose "Try again" re-runs the guard). Only the watcher reads the session unmasked (`useAuthSession({ unmasked: true })`).

Three observers feed it, and none can be skipped:

- **Every session guard** calls `resolveRouteSession()` (`apps/web/src/lib/route-session.ts`): `getRouteSession()`, then the identity check. That is `_auth`, `admin`, `login`, `signup`, `forgot-password`, `reset-password` and the standalone `device`, `mcp-login` and `mcp-consent` pages. A different identity replaces the document and the guard never settles, so no page renders the previous identity's cached data, even for a switch made while no watching page was open. `pnpm policy:checks` rejects any route-file reference to `getRouteSession` or `@/server/auth-session`.
- **The watcher**, `useReloadOnIdentityChange()` (`apps/web/src/hooks/use-reload-on-identity-change.ts`), for a change while a page is open (in a layout effect, before a frame pairs the new chrome with the old data). The `_app` shell mounts it, and so do the standalone pages that show private data outside it (device approval, MCP consent). It also connects the open tabs: Better Auth tells other tabs about a sign-out but not a sign-in, so each newly confirmed identity (seen by the watcher or by any guard) is announced on the document's `BroadcastChannel`, and so is every Better Auth session signal in this tab (`auth-client.ts`: a sign-in, 2FA or sign-up, before the flow navigates); every other tab with a watcher re-checks its session. SSO returns through the login guard (`callbackURL` = `/login?redirectTo=…`), which confirms and announces the new identity before forwarding.
- **The global error toasts** (`router.tsx`): before any toast opt-out, a query rejected with 401 asks Better Auth to check the session (one check in flight at a time) instead of toasting (no toast per mounted query when the session ended elsewhere); a mutation still toasts. Nothing toasts once the document is being replaced.

The router also covers the back/forward cache: a document that ever held a signed-in user's state is hidden as it enters the cache and reloaded when restored, so Back never shows a frozen page nobody re-checked. Anonymous pages are cached as usual.

Browser storage outlives a load, so it carries the identity itself: unsaved document drafts (`sessionStorage`, `use-document-draft.ts`) and the workspace's open tabs (`localStorage`, `lib/kb-workspace/tabs.ts`) are keyed by the user id, so another account in the same browser never reads them; the workspace layout and UI preferences hold no private data. Keep any new persisted private data keyed the same way.

Why a full load, not `queryClient.clear()` or a fresh `QueryClient`: clearing the cache while observers are mounted cancels their fetches silently and can leave the page stuck on a skeleton, `resetQueries()` refetches active queries as the wrong identity (a 401 toast each), and neither stops an in-flight mutation whose late `onSuccess` writes the old identity's data back. A swapped client still leaves Zustand stores and module state behind. A full load drops all of it, and a late callback can only write into the document being discarded. Do not "optimize" it away.

## Shared controls

- **Field outlines.** Inputs, textareas, select triggers, checkboxes and the off switch track draw their border with `--input`, which reaches 3:1 on `--background`, `--card`, `--popover` and `--muted` in both themes (WCAG 1.4.11). `--border` stays light, for dividers and cards. `apps/web/src/lib/theme-contrast.test.ts` checks it. Fills made from the now strong `--input` must still carry muted text: hovered triggers stay at `dark:hover:bg-input/35` or lighter, and menu/picker search fields use an opaque `bg-muted dark:bg-muted` fill with `placeholder:text-muted-foreground` (`lib/theme-contrast.test.ts` scans every `hover:bg-input/NN`).
- **Focus and invalid states.** `--ring` (the focus ring and the focused border) is a strong relative of the app's own `--primary` hue: 3:1 on every surface and at least 2:1 against the resting `--input` outline in both themes, so a focused field is clearly not a resting one (WCAG 2.4.13 style). An invalid control's border is opaque `--destructive` in both themes (no `dark:` `/50`), 3:1 on the surface and on the dark field fill. Outline buttons draw their only edge with `--input`, not the decorative `--border`. `lib/theme-contrast.test.ts` checks all three.
- **Menus.** Every popup surface (`DropdownMenuContent`, `SelectContent`, `PopoverContent`, `Command`) is opaque (`bg-popover`, no blur); `lib/theme-contrast.test.ts` scans every ui component that paints `text-popover-foreground`. A menu that picks one value (the theme menu) uses `DropdownMenuRadioGroup` / `DropdownMenuRadioItem` bound to the current value, so the chosen item is checked.
- **Copy fields.** `CopyField` and `CodeSnippet` share one code size (`font-mono text-xs leading-5`). The copy button sits in its own 44px column outside the scroller, so it never covers text; a long value scrolls inside its box and fades at the edge that has more (`scroll-fade-x`). `CodeSnippet` takes `wrap` for logs and tool output.
- **Scroll cue.** `SelectorRow` and the settings sub-nav fade out at the edge that has more items (`useScrollEdges` in `packages/ui/src/hooks/use-scroll-edges.ts` sets `data-overflow-start` / `data-overflow-end`; `scroll-fade-x` turns them into a mask), and a focused item scrolls clear of the fade.
- **Toasts stack.** The `toast` facade (`packages/ui/src/components/sileo.tsx`) gives every toast its own id, so two toasts no longer merge into one. The pill is one line of at most 350px: `globals.css` caps the header so the icon stays inside, and a message that would be cut off is repeated in the description. Whether a message is cut off is measured at the title's font and root size (`titleOverflowsPill`), not counted in characters: a short message of wide glyphs, or any message at a larger text size, can overflow. Bottom toasts sit above the phone BottomNav (`--bottom-nav-height` in `globals.css`, 0 while no nav is on screen) or above the home indicator, and a toast's action ("Undo", "Try again") is at least 44px tall on a touch screen.
- **Settings that are on or off** show their state in words: a `Switch` named by the setting's title with visible "On"/"Off" text, never only a button verb. A prerequisite the user has not met (their own 2FA before forcing it on others) is an info note with a link that fixes it, and the disabled switch says why beside it. Reference: `apps/web/src/components/admin/security-policy-card.tsx`.

## Public header session hint

Public pages stay static and cacheable: no session lookup and no Better-Auth client on them. `getSessionCookieHint` (`apps/web/src/server/auth-session.ts`) only checks whether a Better-Auth session-token cookie is present, so it is a routing and chrome hint, never an access check. `lib/session-hint.ts` holds it as one query: the `_public` layout seeds it in `beforeLoad` (so a cookie-bearing SSR render already shows Open app), the landing redirect reads the same entry, and the public header reads it with `useQuery` (the 404, outside `_public`, asks on the client). A failed hint reads as signed out. The `_auth` gate writes what it learned (true after a session check, false on its redirect to sign-in), and sign-out writes false. `apps/server/src/ssr-cache.ts` never caches a request carrying a Better-Auth cookie and stores only 200 responses without `Set-Cookie`, so a hint-based page is never served to someone else.

## Form surfaces

The template's form-surface rule (FlyCockpit/template, `patterns/design-system.md` § Form surfaces), as this app applies it. Where a create or edit form lives is decided by its length: a tall dialog that scrolls inside itself hides the action button and the errors below the fold.

- **A dialog is for confirmations and short forms only:** about six controls or fewer, and it fits **without inner scrolling** at 1280×800 and 390×844. `pnpm check:dialogs` fails one that scrolls (§ Dialog fit check).
- **Anything longer becomes a page or a wide side sheet,** using the whole width: sections with headings, two columns of fields from 1024px (`lg:`), one column on phones. A page (`FormPage`, its own route) is the default for creating something; a wide sheet (`<SheetContent size="wide">`) is for editing without leaving the page behind.
- **The quick path first:** the few fields most people need, safe defaults pre-filled, presets where there are many switches; expert fields under collapsed `AdvancedSection`s with a one-line summary of their values.
- **No raw configuration:** key-value pairs use `KeyValueEditor` (rows plus a `.env` text mode), never a JSON textarea; every enum, scope and option has a human label; pickers replace free text.
- **Sticky header and action bar** on every dialog, sheet and long page; **errors inline, focus on the first invalid field.**

In this app: Create API key and Create token are pages (`/settings/api-keys/new`, `/settings/mcp/new`, outside the settings layout so they get the full width); Edit access and API key details are wide sheets. A problem that belongs to a group of choices rather than one field (no knowledge base chosen, a write mode missing) shows under that group as a `FormIssue`, and `focusFirstProblem` focuses the first invalid field or problem in document order (`apps/web/src/components/kb/credential-form-parts.tsx`). A failed attempt that belongs to no field (offline, rejected, could not confirm) shows in the sticky action bar beside Create (`CreateActions`' `alert`), in place of its one-line note, so it is on screen wherever the page is scrolled.

The components, all in `packages/ui` and identical to the template's:

| Surface | Component |
|---|---|
| Short form, confirmation | `Dialog` (`dialog.tsx`): the popup is capped at the visible viewport and does not scroll; its inner body (`data-slot="dialog-body"`, styled through `bodyClassName`, not `className`) does, with `DialogHeader` stuck to its top, `DialogFooter` stuck to its bottom and the close button pinned to the popup. `AlertDialog` (`alert-dialog.tsx`): the popup is the scroller, with the same sticky header and footer. |
| Edit in context | `Sheet` (`sheet.tsx`): `SheetHeader`, `SheetBody` (the one scroller), `SheetFooter` (pinned, outside the body, so the primary action is always on screen); `size="wide"` for a long form (full width on phones, 48rem, 64rem from `xl:`). |
| Long create form | `FormPage`, `FormSection`, `AdvancedSection`, `FormActionBar` (`form-page.tsx`). A layout with a sticky sub-nav sets `--page-sticky-top` to its height, as the admin layout does, so the page's sticky title row pins below it. |
| Numbers in a range | `RangeField` (`range-field.tsx`, `lib/range-scale.ts`): a slider with a typed input, snap stops, units, a marked default and a dynamic limit. |
| Key-value pairs | `KeyValueEditor` (`key-value-editor.tsx`, `lib/dotenv.ts`). |
| Choices | `SelectField` (`text-field.tsx`) |

Their labels come from `useRangeFieldLabels()` / `useKeyValueEditorLabels()` (`apps/web/src/hooks/use-form-field-labels.ts`, strings under `common:forms`); `packages/ui` ships no strings. Sticky header and footer carry the edge padding themselves: never give them negative margins (a sticky box cannot leave its container, so it would be pushed over the content).

**Select fields.** `SelectField` takes its choices as data, `options: { value, label }[]`, never `<SelectItem>` children. Base UI's closed select prints the chosen option's label only when the root gets an `items` map; without it the trigger shows the raw value (`user`, `f16`). `SelectField` passes `options` as that map and renders the items from the same list (`packages/ui/src/components/text-field.test.tsx` pins it). Every `label` is translated; a raw id developers need goes in `description`. A raw `<Select>` outside `SelectField` passes `items` to its root, or renders its own `SelectValue` children (the language switcher does).

**Errors next to the field.** Validation errors appear under the field they belong to, never only in a toast or at the bottom. A failed submit moves focus to the first invalid field: give the `<form>` a ref and `noValidate`, set `onSubmitInvalid: () => focusFirstInvalidField(formRef.current)` in `useForm` (`packages/ui/src/lib/focus-first-invalid.ts`; it opens a collapsed `AdvancedSection` around the field), and leave the submit button enabled while the form is invalid (disabled only while submitting). A `.min(1)` string reads "This field is required." (`apps/web/src/i18n/zod.ts`).

## Route pending states

On a hard refresh of a signed-in page, what paints first is already the app: the same header, sidebar and bottom nav as the loaded page, in the stored theme, with only the content area as a skeleton shaped like that page. Nothing outside the content moves when the page arrives.

The signed-in layout `$lang/_app` is `ssr: false`, so the router renders that route's pending component on the server, and the client keeps it until the layout can mount (hydration, the auth check). So:

- `_app`'s `pendingComponent` renders the shell's own frame (`AppShellFrame` in `apps/web/src/routes/$lang/_app/route.tsx`, the same function the layout renders: skip link, header, `AdminSetupBanner`, `AppSidebar`, `<main>`, BottomNav) around `RouteContentSkeleton`. Only `<main>`'s content waits. `apps/web/src/components/public-shell.test.tsx` pins that the pending frame and the loaded frame are the same markup outside `<main>`. While the session loads, `AppSidebar` draws a skeleton of its own width on signed-in pages (under `_auth` or `admin`), as the BottomNav does, so the content does not narrow when the session arrives; the sign-in pages have no sidebar. (The collapsed rail's width comes from local storage, so a collapsed sidebar can still change width once on a hard refresh.)
- Every pending boundary below it (the router's `defaultPendingComponent`, the forced-2FA gate's settings load in `_auth.tsx`, and the admin layout's, which waits for the same settings so its 2FA nudge arrives with the page instead of pushing it down) renders `RouteContentSkeleton` alone, inside the shell already on screen. There is no route-level spinner.
- Each route declares its shape in `staticData` (`apps/web/src/lib/pending-layout.ts`): `pendingShape` (`"list"`, `"cards"` (the knowledge bases page, the signed-in home: its Owned and Shared sections of KB cards, `lib/kb-grid.ts`), `"detail"`, `"document"` (a KB document's own loading state: title, path, the body at the long-read measure), `"form"`, `"overview"` (the admin overview: a status card, then section cards), or `"auth"` for the sign-in pages' centred card), `pendingWidth` (the `PageShell` width) and, on a layout route that draws chrome around its children, `pendingFrame`: `"admin"` (the admin sub-nav), `"settings"` (the settings title and side nav), `"kb"` (a KB's page shell and breadcrumbs), `"workspace"` (a KB's workspace: from 1024px the file tree at its default width, then the toolbar and the padded pane with the breadcrumbs). A layout whose chrome depends on the page below passes a function of the leaf route's id: the KB layout's `kbPendingFrame` draws the workspace for the KB home and its documents and the page column for its settings and pull requests, as the layout itself does. (The tree's width and whether it is open come from local storage, so a resized or hidden tree can still move the pane once on a hard refresh.) The skeleton draws the frames at or below the loading boundary and the leaf's shape; inside a settings or KB layout, or the workspace, that is already on screen it adds no page container of its own.

A new route sets its `staticData`; a new layout with its own chrome adds a `PendingFrame` and draws it in `apps/web/src/components/route-content-skeleton.tsx`. The header carries `data-app-header` and the BottomNav `data-bottom-nav` for the check below.

## Browser checks

Two real-browser checks enforce the two sections above. They need the global `agent-browser` CLI and a running stack, so they stay out of CI; run them after touching a dialog, the shell, a layout route or a pending state. `scripts/check-dialogs.ts` and `scripts/check-shell-loading.ts` are the template's, unchanged, and `scripts/browser-check-lib.ts` is the template's with this app's consent key and without the template's shared `<main>`/footer probe (this app's `check:layout` keeps its own); `scripts/browser-checks.config.ts` is this app's: how to sign in, the dialogs and the pages. Sign-in goes through the app's own form (`formSignIn`): it waits for the form to hydrate, submits it, and polls with short evaluations that survive the full page load the sign-in ends in, typing a current code when the account has a second factor (`"totpSecret"` in the accounts file). A dialog or page that needs data on the stack says what (`needs`) when it does not open, an unusable accounts file stops the run with what to fix (never its contents), and the cases run grouped by role, so a run signs in once per role.

This app has no mock mode (`MOCK_SERVER = false`). Start a stack (`pnpm dev:docker <port>`), sign up two accounts on it (the first becomes the instance admin; verify through the stack's mailpit), create a KB as the admin, create one personal access token and one API key as the admin (Settings → MCP access / API keys; the revoke dialogs need them), and write their credentials and the KB id to a JSON file outside the repo (the format is in the config's header). Then:

```bash
BROWSER_CHECKS_ACCOUNTS=/path/outside/repo.json pnpm check:dialogs --url http://127.0.0.1:<port> --no-sandbox
BROWSER_CHECKS_ACCOUNTS=/path/outside/repo.json pnpm check:shell-loading --url http://127.0.0.1:<port> --no-sandbox
```

`--no-sandbox` is for Ubuntu 23.10+ (AppArmor) Chromium. Each run uses its own agent-browser session (`check-dialogs-<pid>`, `check-shell-loading-<pid>`) and closes it; `BROWSER_CHECK_SESSION_PREFIX` (optional) prefixes every check's session name, so agents running checks side by side can tell theirs apart. The judging logic has unit tests (`pnpm check:dialogs:test`, `pnpm check:shell-loading:test`, both in `pnpm verify:tooling`).

### Dialog fit check

`pnpm check:dialogs` opens every dialog in `DIALOGS` at 1280×800 and 390×844 and fails when the popup or anything inside it scrolls vertically, when the sticky header or action bar covers content, when the popup reaches outside the viewport, or when the dialog does not open (`--only "<name>"` runs one). List every dialog the app ships, confirmations included; a dialog that cannot fit becomes a page or a wide side sheet and leaves the list. There is no exemption field.

### Shell loading check

`pnpm check:shell-loading` records, on every animation frame from the start of the document, the boxes of the header, the BottomNav and `<main>`, the theme class and whether the content skeleton shows, plus layout shifts. It hard-reloads the pages in `SHELL_PAGES` at 1280×800 and 390×844 with the stored theme dark and the OS light, on a throttled network (150ms, 4 Mbit/s) and CPU (4×), and fails when the first painted frame has no header, `<main>` or BottomNav or is not the content skeleton, when a later frame loses the header, when the header, the BottomNav or the top of `<main>` moves by more than 1px before the page has loaded, when a frame is in the other theme, or when cumulative layout shift exceeds 0.05. On a page with the public footer (`[data-public-footer]`), a shift that only pushed the footer below the first screen of a long page does not count, and a page whose content fits the viewport must show its footer in it; the app shell has no footer, so this applies only to public pages added to `SHELL_PAGES`.

## One h1 per page

Every page has exactly one real `<h1>`, never a `role="heading"` stand-in. An auth page's h1 is its `AuthCard` title (sign-in, sign-up in every mode, forgot/reset password, verify email, the forced-2FA card); Settings has its layout's "Settings" title and its pages use card titles; the 404 is the page's h1 in the public and app shells and an h2 under Settings. `apps/web/src/components/auth/auth-pages.test.tsx` and `apps/web/src/components/page-headings.test.tsx` pin it.

## Guards wait for the shell to hydrate

`_app` is `ssr: false`, so the server sends its pending frame (`AppShellFrame` around `RouteContentSkeleton`, § Route pending states; the frame carries `data-app-shell`) and the session guards run only in the browser. A guard decision that lands while that frame is still server HTML (a signed-out cold load of `/settings` redirecting to sign-in: a different nav state and skeleton shape; or a non-admin's `/admin`, whose `notFound()` renders the public 404 above `_app`) makes React hydrate the new state against the old HTML: React error #418. Every guard probes through `resolveRouteSession()` (`apps/web/src/lib/route-session.ts`), which waits for the frame's first effect (`lib/app-shell-hydration.ts`, at most 5 s) alongside the session probe, then admits the identity (§ Query cache follows identity); never `getRouteSession()` alone. `lib/app-shell-hydration.test.ts` checks the wait and that no route calls `getRouteSession` directly.

## Signed-out forms survive a refocus

Better Auth refetches the session when the tab regains focus and marks every refetch of an empty session `isPending`, the same snapshot as the first load. `useAuthSession` remembers, per document, that the session settled anonymous, so a refetch (or a failed one) keeps the anonymous state and the sign-in or sign-up form stays mounted with what the visitor typed. Only the first load shows the skeleton. Under `SessionUnconfirmed` (the app shell's pending state) and while the identity is unverified (both § Query cache follows identity) the memory is neither read nor written, so that chrome stays pending. `apps/web/src/components/auth/auth-form-refocus.test.tsx` and `apps/web/src/hooks/use-auth-session.test.tsx` check it.

## Admin invites and archive

An invite creates the account without a password and mails one set-password link; spending it sets the password and verifies the address (`onPasswordReset` in `packages/auth`), so there is no separate verification mail. Every completed password reset (including an invite link) also signs out all sessions, revokes PATs, OAuth grants, API keys and their child tokens, and cancels pending CLI and two-factor sign-ins; tools must reconnect. Both sweeps delete the user’s Better Auth `2fa-*` challenges, their linked OTP/attempt rows, session-bound OTPs and `trust-device-*` records. The pre-sweep revokes credentials and deletes all browser sessions in one authority-locked transaction (immediately invalidating their signed cookie caches), before the password transaction; a second credential sweep runs afterward. If reset fails after the pre-sweep, the user remains signed out everywhere with credentials revoked even when the password is unchanged. A failed pre-sweep returns 503 without changing the password or consuming the link, so the same link can be retried; a failed after-sweep is logged with a SECURITY marker, then rethrown after retiring other reset/set-password links and completing invite email verification. The reset form preserves both typed passwords on a pre-sweep 503 and offers a localized retry; only an invalid token shows the invalid-link screen. Browser credential mints recheck the live authorizing session under the revocation lock; invite email verification still runs after failed post-sweep revocation and its failures still propagate.

Residual: if the post-sweep exhausts its retries, a credential created after the pre-sweep may survive. Requests already in flight when reset commits can also finish afterward: a password sign-in verifying the old hash, a two-factor sign-in completion, a change-password request that already verified the old password, an admin impersonation request or a token refresh. Better Auth core verifies before it writes, without a password-generation check; successful sweeps do not close this entire class. The proposed follow-up is a password-generation check under the credential authority lock at session insertion and password writes. Change-password’s credential sweep runs after the password commits; a failure there is logged with a SECURITY marker and rethrown, without rolling back the committed password.

The admin picks the invitee's **Email language** (default: the admin's own); it is saved as `User.locale` from the first insert and used for the invite mail and the link's page. Archive is confirmed first (the dialog says tokens and connected apps are revoked for good); its success toast carries **Undo** (8 s), which restores the account's sign-in like the row's Restore (`users.unarchive`), not the revoked credentials.
