# CLI: private local and remote KBs

`kb` is an Apache-2.0 Rust CLI and stdio MCP bridge. Local and remote backends
advertise the same complete kb/1 catalog and validated schemas. Diagnostic logs
use stderr; stdout belongs to command JSON or MCP. No credential-print command.
The [CLI README](../apps/cli/README.md) has detailed custody and model examples.

## Install

Download `kb` 1.0.0 from [GitHub Releases](https://github.com/FlyCockpit/knowledge-base/releases). Releases provide platform archives, shell and PowerShell installers, `sha256.sum` checksums and `THIRD_PARTY_LICENSES.html` generated by cargo-about. Verify your archive against the release checksum file, for example on Linux x64:

```sh
grep 'kb-x86_64-unknown-linux-musl\.tar\.xz$' sha256.sum | sha256sum -c -
```

The Linux archives (`kb-x86_64-unknown-linux-musl.tar.xz`,
`kb-aarch64-unknown-linux-musl.tar.xz`) contain a fully static binary: no
glibc version floor and no C++/OpenMP runtime to install; local embeddings keep
llama.cpp's OpenMP threading. Being static, the Linux binary resolves host
names from `/etc/hosts` and DNS only: it does not load NSS modules, so names
that only resolve through `/etc/nsswitch.conf` plugins (mDNS `*.local`, LDAP,
sssd) need DNS or an `/etc/hosts` entry. macOS and Windows binaries link their
platform C++/OpenMP runtimes, as described in the build requirements below.

## Build and platforms

The workspace is outside pnpm/Turbo. Build from `apps/cli` with Rust 1.96+
(the pinned CI toolchain is 1.96.1), Git, CMake, a C++ compiler, libclang resource
headers and OpenMP; linked C++/OpenMP runtimes must exist on the destination.
See [vendored native build pins](../apps/cli/vendor/README.md). Native builds use
at most three jobs; reuse the existing target directory for incremental work.

```sh
cd apps/cli
CARGO_BUILD_JOBS=3 cargo build --locked -p kb
cargo fmt --all --check
cargo test --workspace --all-targets --locked
cargo test --workspace --doc --locked
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
cargo xtask sync-docs --check
cargo deny check
```

Release targets are Linux static musl x64/arm64, macOS x64/arm64 and Windows
MSVC x64 (Windows 10+ native locking/ACL support). The musl binaries are built
in the digest-pinned Alpine builder (`apps/cli/ci/musl-builder.Dockerfile`,
static `libgomp`/`libstdc++`) and run the same real-model lane as the GNU
development builds. Native CI must
execute durability, drain/ACL and real-model checks on each supported platform;
cross-compiling alone does not demonstrate platform behavior. Missing platform
execution is an incomplete release result, not permission to drop a platform.

## Remote login and stdio

**Stdio protocol.** `kb mcp` (local or `--server`) speaks MCP 2026-07-28 over
newline-delimited stdio, like the server's stateless HTTP endpoint: a request
whose `params._meta` carries `io.modelcontextprotocol/protocolVersion` and
`io.modelcontextprotocol/clientCapabilities` is served on its own, with no
`initialize` or `server/discover` first. A request without that envelope needs
a session: `initialize` plus `notifications/initialized`, or `server/discover`.
A present envelope is always checked, in a session or not, field by field as
the MCP SDK checks it (`clientInfo`, every `clientCapabilities` shape,
`logLevel`, `progressToken`): a malformed one is
`-32602 Invalid _meta envelope…` (`data.envelope` names the key), and any other
version is `-32022 Unsupported protocol version: <v>` with
`data: {supported: ["2026-07-28"], requested}`, the error the MCP SDK sends.

```sh
kb config set-server https://kb.example
kb login --name Laptop
kb mcp --server https://kb.example
kb logout
```

Login prints a public verification URL/code; open it yourself and compare the
code before approving. Nothing is preselected: choose KB bits, optional creation
bits and dated expiry. Pending/slow-down polls do not consume approval. Denied,
expired or lost consumed exchange requires new login; no retained server token
secret can be replayed. PATs are separate from browser sessions.
Import an existing PAT with `kb login --token-stdin` from a private pipe or
`kb login --token-file /private/token`; never use token argv or a secret URL.
Files must be owner-only regular files, no symlinks/reparse points or hard links.

Credentials live in the private data-dir credential store (the per-user data
directory, overridable with `KB_DATA_DIR`; unrelated to the server's
`KB_DATA_ROOT` volume), keyed by canonical
origin AND exact `/mcp` resource. Config/server changes never forward another
origin's token. Unix uses 0700/0600, atomic publication and file/directory fsync;
Windows uses DPAPI CurrentUser and a protected current-SID-only DACL, failing
closed when protection is unavailable. Credential I/O is locked and recovers
recognized interrupted temp writes. Config stores neither token nor device code.
HTTPS is required; explicit `--allow-loopback-http` permits development loopback
only on each command, or for one server once remembered by
`kb config set-server <url> --allow-loopback-http`. Redirects and ambient proxy env variables are ignored/
rejected as appropriate. Opt into a proxy only via config `proxy`, without URL
credentials. Remote startup verifies the server's tool list before advertising
it: a non-empty subset of the pinned catalog, in catalog order, with pinned
schemas except an optional `kbId` enum (or the never-matching `not: {}` when no
KB qualifies). The agent sees exactly that list and the
server's instructions; other tools are refused locally. `--read-only` lists
only read tools (write tools are neither advertised nor callable). Calls make one attempt; lost mutation replies
have unknown outcomes, so retain arguments/idempotency key for recovery.

Default logout self-revokes the presented PAT before deleting matching local
state. Network failure retains it for retry and reports uncertain revocation.
`kb logout --local` deletes local material only and states that remote authority
remains active. A concurrent re-login's replacement credential is preserved.
EOF/cancellation drains in-flight HTTP; sealed forwarding keeps ciphertext.

## Durable local store

```sh
kb config set-root /private/store          # default for every local command
kb mcp                                       # or: kb mcp --root /private/store
kb mcp --read-only
kb mcp --tools propose --kb <kbId>,<kbId>
kb model list
kb model enable                              # Gemma 1K: download, verify, probe
kb providers attach --kb <kbId> --provider builtin
kb model status
kb providers list --json
```

`kb config init` writes a commented template; `kb config show` prints the
effective settings. Invalid TOML reports the config path, line and column;
unknown settings are rejected so typos cannot silently use defaults. Fix the
file before running a setter if its TOML is invalid. `root` and `models_dir` must be absolute (MCP hosts start
`kb` from arbitrary directories); `kb config set-root` resolves a relative
argument once, when it is set. `kb mcp`, `kb model`, `kb sealed` and
`kb providers` use `--root`, else the config `root`. Read-only commands
(`kb model status`, `kb providers list`, `kb sealed owner`) never create a
store; a directory that is not empty and has no `state.sqlite` is reported as
"not a kb store" instead of being adopted.

Built-in models (details in [embeddings](./embeddings.md#local-cli-built-in-shared-cache-and-worker)):
`kb model list` shows every model and context tier with its memory estimate,
whether it is downloaded and the recommendation; unknown models or tiers list
the valid ones. `download` fetches into the per-user cache (progress on
stderr; `--json` reports the path, size and checksum), `enable` downloads if
needed and load-probes the choice for this store, `disable` keeps the file,
`verify` re-checks every cached file's SHA-256 and `remove <model>` deletes
`kb`'s own copy (it asks you to type the model ID; `--yes` skips that, and is
required without a terminal). No store blocks a removal: like the server's
Remove, stores that have the model enabled search by keyword with the
`EMBEDDING_PROFILE_UNAVAILABLE` notice until it is downloaded again, then
hybrid again with their existing index (same fingerprint, no rebuild). All
stores share one cache and one embedding worker, so two `kb mcp` sessions (or
stores) search concurrently with one model in memory. The worker only ever
loads a file `kb` created itself (exclusive creation, owner-only from the
start, filled from the stream it hashed, its creation mark recorded: device,
inode, size, mtime, ctime, mode and owner; on Windows file ID, ChangeTime and
owner-only ACL) in the owner-only `verified/` directory of the platform cache,
in place for as long as that mark still matches. Any later `chmod`, ACL change
or write moves ctime, so a file that was ever loosened (or written through a
handle kept from then) never matches again and loads from a fresh copy
instead. Downloads always go to `verified/`. A configured `models_dir` is only
ever read, never written to or deleted from: a model already there (another
program's download) is copied into `verified/` once while its checksum is
checked, then reused, which costs one extra copy of each such model (about
0.31 GB for Gemma, 0.64 GB for Qwen); `download`/`enable` say so on stderr.
`remove` (and a download replacing a damaged copy) deletes only in
`verified/`, by name, after opening that directory once without following
links and proving it is the owner-only directory `kb` created (its recorded
identity); every file in `models_dir` is kept and reported with the reason.
Removal records an owner choice in the private cache: a kept source is not
copied back by searches or status checks. Run `kb model enable` or
`kb model download` explicitly to use it again.
Threat model: only processes of your own user can change entries in that
owner-only directory, and such a process could delete the file itself
anyway; another user can neither redirect `verified/` nor swap it. `disable` and
`remove` succeed only with proof the model is released: the worker's
authenticated acknowledgement, or its lifecycle lock showing no worker is
alive. Without that proof (a request using it is still running, the worker
is stalled or cannot be authenticated) they fail with `DEADLINE_EXCEEDED`
(`remove` then deletes nothing) and can be retried. `kb model status` reports
a worker that is alive but does not answer as "running but not responding",
and one that cannot start here (for example a socket path too long without
`XDG_RUNTIME_DIR`) as "cannot start" with the reason (`workerError` in
`--json`). `kb mcp` says the same on stderr, at startup when a built-in is
enabled and once per new reason after a failed start; searches meanwhile use
keyword search with the `EMBEDDING_PROFILE_UNAVAILABLE` notice.

Local rate limits are the store's own, far above the server's
multi-tenant budgets but still bounded so a runaway agent loop stops: 600
searches per KB per minute (server 30), 60 KB creations per hour (5), 30 index
rebuilds or profile switches per KB per hour (3), 30 provider probes per minute
(5), 600 writes per actor and KB per minute (60) and 1 GiB of staged uploads per
hour (100 MiB). Every hit is a durable `RATE_LIMITED` with `retryAfterSeconds`.

A root is a managed multi-KB store, not an arbitrary worktree. `state.sqlite` is
not disposable: it owns stable store/KB identities, authority, receipts/journals,
PRs, providers and sealed metadata. A nonempty store without it fails
REPAIR_REQUIRED; do not delete it to rebuild search. `repos/kb_<id>.git` and
assets retain canonical history. `indexes/<kbId>/<generationId>.sqlite` files
are rebuildable derived FTS5/sqlite-vec generations; missing indexes clear the
active pointer and rebuild from Git/pinned profiles. Back up the entire private
store with its OS-keystore custody, while its processes are drained; a remote
server bundle is not a local-store import command.

Pull requests in a local store follow the server's conflict-resolution rules on the same
logical merge (see [MCP](mcp.md) "Proposals"); documents changed on both sides
are line-merged by `git merge-tree --merge-base`, as on the server, so merging,
moving a PR onto main and every PR status need Git 2.45 or newer: `kb mcp
--root` checks the installed Git once at startup and refuses MCP initialization
and discovery with a typed `STORAGE_UNAVAILABLE` diagnostic naming the found and
required versions. Merge and publication planning happens in a disposable object store
inside the operation's scratch directory: status reads and refused plans leave
the repository's objects untouched, and a publication promotes only the
objects its commit needs.

Local locks are persistent store then sorted KB locks, with descendant-inherited
leases independent of stdin. Unexpected refs fail closed; never delete lock files
or externally edit managed refs. On Windows, Job Objects drain old descendants
before successors enter. The store owner is trusted; its own malicious path
swaps are outside the jail's protection. `--principal` selects a local configured
capability principal; it is unavailable for remote mode. With no backend flag,
config selects root/server; if both are set choose explicitly.

The store owner holds every permission, so owner writes always reach `main`
(even with `--tools propose`). For a reviewed flow on a local store, create a
narrower principal and serve the agent as it:

```sh
kb principals create --kb <kbId> --access propose   # prints the principal ID
kb mcp --principal <principalId>                    # the agent's session
kb principals list
kb principals remove <principalId>
```

Access levels are `read`, `propose` (writes become the agent's own pull
request, never `main`), `write`, `review` and `manage`. As on the server,
`manage` grants everything; `write` implies `propose`, which implies `read`;
`review` implies only `read` (a review principal cannot edit). The owner's own session reviews and merges with
`knowledge_pull_requests_review`. Removing a principal revokes it on its
sessions' next call.

`--tools <group|preset,...>` and `--kb <id,...>` scope a local connection the way
a server grant's tool groups and KB list scope a remote one (remote connections
are scoped in the web app instead, so both flags require a local store). Groups
are `read`, `edit`, `assets`, `export`, `pull_requests`, `index_admin`,
`kb_admin` and `sealed`; presets are `read`, `propose` (read, edit,
pull_requests) and `direct` (read, edit, assets, pull_requests), read from the generated
protocol artifact. The default is every group and every KB. A `--kb` ID the
store never had is rejected at startup; a deleted KB's ID is accepted with a
warning (its delete receipt stays replayable) and exposes nothing else. With five or fewer KBs, `initialize` instructions name
them (quoted user data), as the server does. Each `tools/list`
is rebuilt from the store's current state, without recovery or other side
effects: it shows the selected groups' tools that the principal's ceilings (and
create capability) could ever satisfy, in catalog order, plus
`knowledge_bases_list` and, when a listed tool writes, `knowledge_bases_get`.
Deleting a KB is owner-only. With `--kb` or `--principal`, each `kbId` carries
an `enum` of the readable KBs that meet that tool's minimum access, and
`source.kbId` of the readable ones (none above 25). KBs created, deleted or
revoked during the session show on the next list. Calls are decided before any
domain work: a tool outside the selected groups, or an asset operation, upload
kind or `--read-only` write the groups do not allow, is FORBIDDEN, and a KB
outside `--kb` is NOT_FOUND. The two supporting tools stay callable.
`knowledge_bases_list` pages over the selected KBs only (its cursors are bound
to the selection), and a KB the connection creates joins its selection.
`--read-only` intersects with both flags. The store owner holds every permission, so presets select
groups only: `propose` does not stop the owner's edits from reaching main.

Provider registration uses `kb providers ... register --idempotency-key ...`
with `--key-stdin` or a private `--key-file`, exact endpoint/model/dimensions
(the endpoint is used verbatim; most providers expect a URL ending in
`/embeddings`, and `register` warns otherwise); probe a revision with
`kb providers probe --provider <id> --revision <n>` before attaching it with
`kb providers attach --kb <kbId> --provider <id> --revision <n>`. Attaching the
profile a KB already uses is a no-op (no rebuild, no rebuild budget spent) only
while a semantic generation of exactly that provider, revision and fingerprint
for the head is active (`state: CURRENT`) or building (`PENDING`); a current or
building keyword-only index never counts. Every `kb providers` and `kb sealed`
command prints a sentence; `--json` prints the machine-readable reply.
`kb providers list` shows each revision's status (`ready`, `revoked`, or
`unavailable` until a successful probe) and the enabled built-in as `builtin`. Credentials live only in the native OS store
(macOS Keychain, Windows Credential Manager, Linux Secret Service). Unavailable
keystore (including headless/container sessions) fails closed, with no plaintext
file/SQLite fallback. A key removed from a reachable keystore outside `kb` is
reported by owner: a provider revision's API key is recovered by registering
the key again as a new revision (`kb providers register --provider-id <id>`)
and attaching it; the store's sealed master key is never regenerated, so that
store's sealed values stay unreadable and cannot be enrolled again there
(`kb sealed revoke` still works without the key; a new store has its own key).
Both local built-ins start disabled; enable defaults to
Gemma/1K, download verifies commit/SHA, and disable drains while retaining cache.
An external provider remains available for low-RAM hosts. See [embeddings](./embeddings.md).

## Downloads and sealed host custody

```sh
kb export --kb abcdefghijklmnopqrstuvwx --output /private/knowledge.zip
kb export --kb abcdefghijklmnopqrstuvwx --kind assets --output /private/assets.zip --json
```

`--rev` pins a commit, `--idempotency-key` recovers the identical prepare.
Bounded frame retries use the same offset; verify size/SHA-256, fsync a new
private destination (existing files refused), then acknowledge with the preparing
PAT. `acknowledged:false` means the ZIP is valid locally but server completion
is uncertain; its ten-minute EOF grace reclaims the slot. See [assets](./assets.md).

Human local `kb sealed --root ... enroll --kb ... --idempotency-key ...`
reads bounded UTF-8 only through `--stdin` or `--file`, returning an opaque token.
`grant` approves one exact consumer/recipient public key/expiry (the owner's
own consumer ID is printed by `kb sealed owner`); `revoke` destroys ciphertext
and approvals and lists the documents that still mention the record. Those
documents keep the symbol (search redacts it) and stay editable: only a changed
document must reference live records, so a revocation never blocks unrelated
writes. No local MCP plaintext tool exists.
For remote device recipient enrollment, login's `--recipient-key-file` points to
an existing private X25519 host key; only the public descriptor is uploaded.
Compare it before explicit exact-record approval; enrolled 2FA is required.
Keep private material for the separate kb-client host resolver, never the agent
stdio transport. [Cockpit seam](./cockpit-adapter.md) explains this boundary.

Remote asset/export commands keep the same protocol with S3 enabled on the
server. Asset misses stream through verified bounded cache; ZIP source misses
read remotely without admitting/touching cache. Downloaded ZIP artifacts remain
local to the server until transfer completion. Live authorization still applies
to every frame. The CLI needs no bucket credentials and its local disk store is
unchanged. See [asset operation](./assets.md#opt-in-s3-operation-and-role-configuration)
for full-object Range costs and outage behavior.
