# Users & Roles (security-critical access matrix)

Unspecified access is denied. Cell vocabulary for live procedures is exactly `allow` / `deny` (empty means deny). All listed procedures are live; there are no handler stubs. Root `appConfig` is public and covered by the shipped baseline (the checker only tokenizes dotted procedure paths).

Roles: **anonymous**, **user** (authenticated), **admin** (instance admin). Admin is not an implicit private-KB reader or manager.

KB bits (not instance roles): `manage => write, review`; `write => propose`; `propose => read`; `review => read`.

## Authn / authz mechanics

- Better Auth `admin` plugin. `ADMIN_EMAIL` is one trimmed lowercase identity. First-admin selection and role assignment share a database transaction with user insert via the wrapped adapter.
- After bootstrap completes, `ADMIN_EMAIL` never re-promotes a demoted user. Deleting the chosen user nulls the FK and never resets completion.
- Public signup, admin invites, and private no-SMTP invitation links remain. Disabled public signup still accepts admin invitations.
- Human-only: shares, transfer, credential/mirror/sealed enrollment. Those are not MCP tools. Invitation and transfer receipts reauthorize the live identity and current manage/owner rights before replay, without repeating effects or charging the mutation budget.
- Instance policy, role, archive and unarchive writers use the registered live-admin builder: authority lock, current actor/email/ban/2FA checks, and effect share one transaction. Outgoing 2FA policy/identity writes preserve exact grant generations and grace deadlines through row waits and outer adapter callback delays; paired grant/PAT tombstones commit with the update. Rollback discards both, and an on-time enrollment keeps its existing generations.
- KB share invitations and ownership-transfer offers are emailed through the `kb-email` durable job; SMTP never runs in the request. The invite response, its code path and the email template are identical whether or not the address has an account (the address is only resolved by the worker); the share email also links to sign-up, which returns to the acceptance page. The copyable acceptance link stays in the UI as the fallback, and without SMTP it is the only delivery.
- The members list (manage only) shows each member's display name. The address an accepted invitation was sent to is shown only to the KB owner and to that invitation's sender, and only while it is still the member's address. A manager changes a member's permission bits in place (`kbs.shareUpdate`, the same `manage` authority as invite and revoke); the share keeps its owner-set sealed-values flag.
- Email delivery rechecks the exact pending request and live identities: invitations require current inviter manage; transfers require the pinned owner/version and a live accepted recipient with read. SMTP connection/login and retry waits run outside authority. The existing coordinator owns the shared authority lock and a transaction holding the durable job row, checks its live epoch/lease before the effect, and holds both through the final SMTP send (three-second abort deadline). The transport destroys and drains its owned socket before releasing the gate; revocation or cancellation either wins before send or waits for that authorized attempt. SMTP acknowledgement loss can still duplicate delivery on retry. Invitation addr-specs are ASCII, at most 64 local-part octets, 63 per domain label and 254 total; SMTP_FROM accepts exactly one mailbox with an optional bounded display name.
- KB blobs use content-addressed storage under `assets/` in `KB_DATA_ROOT` by default, with optional S3 authority and a bounded local cache. Git manifests define membership and historical lineage; see [asset storage](./assets.md).

Asset list requires live KB read, reachable revision, manifest membership and retained lineage. Put requires propose and actor/KB/kind-bound READY upload; import requires source read plus target propose at reservation under sorted KB locks. Propose-only publication changes the actor-owned PR branch. Receipts reauthorize target propose; an authorized copy survives later source revocation.

Exports require live KB read and the preparing actor; no instance-admin bypass. The same-origin `/kb-exports/:kbId/:transferId` session route uses the same immutable artifact and frame admission. ZIP receipts expire 15 minutes after preparation begins, never on sliding reads. EOF is returned on the last nonempty frame; offset equal to size is invalid. One live (WRITING or READY) artifact per user, two per server; cancellation, failure and expiry reclaim capacity. Completion: the client acknowledges the finished download (`kbExports.complete`, MCP `knowledge_export_complete`; only the preparing actor, with live read), which marks the artifact DOWNLOADED (ABORTED if its last frame was never served), deletes its file and releases the slot at once; a repeated acknowledgement is an idempotent success. Serving the last frame does not delete anything: it starts a fixed 10-minute grace window (the receipt's expiry becomes that frame's time + 10 minutes, once), during which frames stay readable and the slot stays held, so a lost last reply is retryable; when grace expires without an acknowledgement the durable expiry sweep (startup and every 60 s) marks it DOWNLOADED, deletes it and releases the slot. Terminal failure (storage failure, cancellation, a torn-down partial stream) still releases immediately. A released transfer is no longer readable and its prepare receipt no longer replays. EOF holds the authority lock before the artifact row lock through grace validation, final read/transport authorization, and ZIP frame emission; denied or cancelled first EOF rolls back its grace. A previously delivered EOF keeps its fixed grace when another read fails. Stream failure and shutdown join pending reads and reclamation before settling; downloads still awaiting admission are included. Acknowledgement checks live read under the shared authority lock in the transaction committing its terminal state; file reclamation follows that commit. Expiry pages are candidates only: reclamation rechecks current state and expiry while locking the artifact row, commits terminal intent before unlink, and retries failed cleanup at startup or the next sweep. A concurrent EOF grace update that wins the row race remains readable; an already terminal artifact cannot be resurrected. The Rust `kb export` command uses the typed MCP client to verify exact size and SHA-256, durably publish a new destination file, then acknowledge with the preparing PAT. Failed acknowledgement retains the saved file and uses the same grace fallback.

Providers require a live browser identity and exact ownership, including instance admins acting as users. Create/probe atomically encrypt a new immutable revision and enqueue its durable probe; both charge the shared 5/minute user probe budget. Max 20 unrevoked providers, 50 immutable revisions per provider, and 1000 total revision rows per user (revoked history still counts). Pending/failed probes project as unavailable; only completed probes project as ready. Revoke and account removal erase all revision ciphertext and fence late results. Profile attachment and rebuild require live manage, confirm RUN, and the 3/hour KB rebuild budget. Attachment requires the caller’s own usable immutable provider revision, or the ownerless built-in SYSTEM_BUILTIN revision, which any live manager may attach. Index status/profile reads require live read; instance admin grants no KB access. Worker builds pin source/profile and activate only through the desired-epoch CAS. Revocation cancels builds and makes the old index unavailable. Instance admins (404 to everyone else) select and enable/disable one pinned built-in artifact (EmbeddingGemma 2 or Qwen3-Embedding-0.6B, 1K/2K/4K/8K context; fresh instances default to disabled Gemma 1K): enable increments the model epoch and creates one durable download job; disable increments it, cancels that job and releases its disk reservation atomically. Only the worker downloads (pinned HF URL/hosts, verified size+SHA-256), then the real forked model child must load and embed the verified file (runtime probe; failure is MODEL_RUNTIME_UNSUPPORTED) before an epoch CAS reaches READY. Each human mutation rechecks live role, verified email, ban and forced-2FA policy inside the authority transaction before effects, including replay/no-op paths. Admin status grants no KB access. Only READY is executable: it creates the system SYSTEM_BUILTIN provider revision that every signed-in user can list and attach. Disable leaves READY, so new builds and queries become unavailable and late results fail their fences. SYSTEM_BUILTIN embedding runs only in the worker's forked child; the API server never loads the native addon. Instance admins also set the built-in runtime config (model and context tier, plus Qwen K/V cache types; Qwen uses batch 512, Gemma uses the full input, and flash attention is fixed): the server rejects an option estimated at or above 90% of the worker-reported memory budget and requires an explicit acknowledgement above 70% (unknown budget fails closed). On a READY model a change is only queued: a worker first load-probes it (load + one max-context embedding; side by side when both children fit under the 90% level, otherwise the running config is stopped first and search is lexical-only with an EMBEDDING_RUNTIME_RELOADING notice meanwhile). The worker rechecks candidate admission against its current detected memory limit before downloading, and every native child spawn (initial capability/max-context probe, pending probe, serving and token-measurement reload) checks that worker’s current limit; unknown or blocked budgets cannot load a model. Side-by-side loads also recheck the combined estimate at spawn. A failed or interrupted probe leaves the last good config active and shows the admin a fixed error code. Hybrid and all structured searches share one absolute deadline of at most 60 seconds (shortened by the caller), including embedding admission, any permitted pre-search lexical continuation, SQL reads and final authorization; fallback never restarts the budget or charges a second query. Every search page spends one shared 30/minute user+KB query point and holds one of four per-user query slots across transports through final authorization and SQL drain. Structured rows that cross ordinary or model-context windows retain separate immutable row citation spans; embedding pieces still respect the model context, and queryless pages deduplicate overlapping row matches. Only a successful probe creates the new SYSTEM_BUILTIN revision/fingerprint, retargets every attached KB and re-embeds them one at a time deployment-wide, ordered by a stable snapshot of the most recent admitted search (including queryless structured pages); all built-in build executors, including ordinary commit and manual jobs, hold one deployment-wide session permit until work drains, while external-provider builds retain their two global slots; waiting KBs keep serving search from their previous-settings index with an EMBEDDING_REBUILD_PENDING notice. With the built-in model, chunks are split to fit the configured context (overlapping pieces, exact source spans), so builds never fail for input length. The admin sees progress by opaque KB id only, never KB names or content. Under the model-volume lease, cleanup retains selected/pending artifacts and all non-PURGED or live-leased generation references; PURGED cursor tombstones no longer pin obsolete weights. Ordinary live download retries keep their resumable partials, while settled or abandoned candidate partials are reclaimed. A non-expiring process permit serializes ordinary downloads, model-file preparation and cleanup until their filesystem operations and children drain; a DB lease timeout cannot transfer that permit. The native worker volume fence drains a dead worker and its descendants before replacement, which can reclaim the expired DB lease. Terminal model outcomes, quota settlement and the acquired durable-job attempt tuple commit in one authority transaction, so interruption cannot strand a completed job in DOWNLOADING. A durable publication intent precedes artifact fsync/close/link: writeback, close or publication durability failures discard the affected file, and restart recovery discards incomplete publication before accepting cached bytes, while a durable completion receipt preserves an already-published verified file after a crash.

Built-in serving requests retain cancellation from the first readiness read through queue admission, lease acquisition, loading, token measurement, embedding, the one crash retry and the final readiness fence, with a shared 120-second deadline. Cancellation kills and reaps the owned child before settling that request. The separate configuration probe has the same 120-second default budget starting before acquisition; supervisor shutdown owns and drains it too. Download verification receives the download attempt's disable, supersession, and shutdown signal; its configuration read and native probe share one 120-second budget, and it retains its volume permit until SQL and every verification child drain. One heartbeat serves all model-volume holders; renewals and config-claim heartbeats are single-flight and joined before release or settlement. Model readiness, configuration, memory reporting and lease SQL use dedicated owned connections with five-second default connection/transaction limits, shortened by an operation's remaining deadline. Cancellation terminates only the owned backend, joins the acknowledgement and receive path, and retains startup transaction/idle limits when replies are lost. Lease renewal and release use fresh database time after row acquisition and the acquisition fence. These operations never queue in the shared Prisma pool. Budget reports are single-flight; native peak reports retain one current write and one latest observation. Worker shutdown closes report/watch admission, cancels outstanding reads/writes and joins them before releasing clients or model ownership.

Local `kb providers` control requires the store's human owner. Registration requires `--idempotency-key`; retry with the same key and input resolves the same immutable revision and operation ID, including after a native write or SQLite finalization failure. Changed configuration or credential bytes with that key are rejected. Credentials use only the native OS store; unavailable services fail explicitly. Native work has a separate account fence and a bounded child supervisor, so it does not hold the global store fence. Revocation commits before native cleanup and retries unfinished deletion. Local probes share a durable five/minute owner budget (failed attempts count), and the same 20 live providers / 50 retained revisions per provider / 1000 retained revisions per owner caps apply. Registration itself does not dispatch a probe; the owner invokes `probe` separately. Provider key input permits up to 16 KiB printable ASCII from private files or noninteractive stdin; PAT input retains its stricter alphabet and 8 KiB bound.

PR reads require live KB read and recheck before reply. Creation requires propose and an owned USER branch. Merge requires review (write does not imply review), MERGE confirmation, and both viewed source/main SHAs. Close requires review or the original actor with live propose and DELETE confirmation. Closed/merged source branches remain retained and immutable. Diff cursors bind actor, KB, PR, base, head, target and expiry; follow all pages to complete a large diff. Clean divergent merge commits use main as first parent; content/provenance conflicts require the author to update the branch. Main publication, PR merge state, audit and desired-index scheduling finalize in one journal transaction. Same-key retry returns the recorded result after live authority recheck.


Sealed controls require a cookie/browser identity, live ban/2FA policy, enabled two-factor authentication independently of global forcing or enrollment grace, and current KB ownership; manage shares and instance administration grant no authority. Sealed-value capabilities are held only by the KB owner or by a member whose live share has the owner-set `includeSealedValues` (default false when a member's share is first created; re-invites, re-acceptance and permission changes of a live share preserve it; removing a member, by the owner or a manager, ends the share and removes the sealed approvals bound to that member's PATs on the KB, so a later re-invitation creates a new share that starts false and cannot resurrect an old approval; ownership transfer always leaves the former owner's retained share false); only the owner can change it (`kbs.shareSetSealedValues`). A share without it never yields a sealed-value capability, whatever its bits: a PAT approval names a live PAT generation whose holder is eligible at grant time, and resolution rechecks the resolving user's eligibility live. OAuth grants never hold a sealed approval: an OAuth consent approval that requests sealed recipients is rejected with the typed `SEALED_VALUES_REQUIRE_CLI_OR_PAT` error ("Sealed values require the CLI or a personal access token.") and creates no grant, and resolution refuses OAuth credentials; only PATs, including CLI device-flow PATs, can. Accepting an ownership transfer leaves the former owner an ordinary `manage` share (which the new owner can remove) and retires the new owner's own member share; it also moves the KB's sealed records to the new owner and removes approvals the former owner issued on them; resolution additionally requires the approval's authorizer to be the KB's current owner. Enrollment accepts at most 16 KiB of well-formed UTF8 and an optional absent record UUID under the computed attachment namespace. UUID/version tombstones forbid reuse after revoke. Exact approvals pin consumer kind and ID (the exact PAT grant ID, including CLI device-flow PATs; local-store approvals remain on-device), record, usable recipient X25519 key UUID/public bytes (rejecting low-order points), and UTC expiry with seconds and at most three fractional digits. Direct and device approvals reject finer expiry spellings before storage so PostgreSQL and JavaScript Date preserve the authorized instant exactly. Device recipient selections require live enrolled 2FA at selection, approval and exchange; ordinary selections without sealed recipients retain the general forced-2FA policy. No wildcard, list, or literal-read procedure exists. Revoke and KB/account teardown destroy ciphertext and grants while preserving record/receipt tombstones. Enrollment and grant retries recheck live record authority; receipts/audit return metadata only. Whole-tree publication checks live same-attachment enrollment under the authority reservation; an already reserved COMMITTING publication may finish after revocation. Historical source reads retain the symbol. Origin changes require explicit reenrollment. Recipient-encrypted resolution requires current read, an exact live consumer/key approval, and the reference at the pinned source path/revision; authority is rechecked before wrapping. Both source reachability passes and all tree/blob reads share one total resolution deadline (at most 60 seconds, shortened by the transport or caller). Cancellation and timeout terminate and join each owned Git child before the MCP admission permit is released. Envelopes expire within 60 seconds and never contain plaintext. Live OAuth/PAT registry linkage and the common MCP data-plane bindings enforce this boundary; the complete tool and oRPC exclusion inventory is in `docs/mcp-tool-coverage.md`.

MCP credential minting, listing and consent are human control-plane only: cookie session plus live ban/forced-2FA admission on the authority session for mint/list/revoke, never a bearer token, never an MCP tool. Instance admin permissions exclude impersonation, password/email takeover and generic user updates. Legacy impersonated sessions cannot use application or library credential/control/data entry points, even after their initiating admin is demoted or removed; signing out remains available. Each PAT owns one random-UUID grant generation. `GrantKbAcl` is the only stored KB ACL; the PAT row keeps only lookup prefix, secret digest, grant reference, scope snapshot and expiry (the human mint takes an omitted expiry = 90 days, a dated expiry up to 365 days, or an explicit null = never expires; the device flow always mints a dated PAT; no refresh/offline_access). Mint runs under the authority lock and the user row lock, allows at most 10 live PATs per user, and rejects (never clips) any requested bit, expanded, that the user does not hold live. `allowCreate` defaults false; `createdKbBits` must be empty unless creation is allowed, then must include read and the grant must carry literal `mcp:write`. A token-created KB validates its persisted creation bits against the current ceiling when PREPARED becomes COMMITTING, then appends only that KB with the reserved bits at journal finalization; ownership never widens it and other grants gain nothing. Token authority is always the stored grant ceiling intersected with live owner/share bits, checked with scope, expiry, the exact live generation, ban and forced-2FA state through the grant verifier; a digest match alone is not admission. Revoke, `users.archive`, a permanent Better Auth ban (no `banExpires`) and account removal tombstone grants under the authority lock. A temporary (dated) ban only suspends: admission refuses while the ban holds and admits the same credential again once it lapses or is lifted; suspension is never stored on a credential, so a lifted ban cannot resurrect one revoked for another reason. Forced 2FA keeps an unenrolled user's grants live during the enrollment grace and revokes them once it ends: bearer admission settles the full live role/policy/grace/enrollment predicate under the authority lock; enrollment, role and policy writes settle any due lapse before changing its evidence and settle newly imposed requirements afterward. The existing daily auth cleanup scheduler also settles quiet holders. Grant and PAT tombstones commit together; a stale admission cannot revoke a generation issued after enforcement is relaxed. Tombstones are permanent, so unban/unarchive/enrollment/re-consent never reactivate an old generation. Account deletion nulls the live user FK but keeps grant, ACL and sealed-approval tombstones. Sealed pat approvals must name an existing live PAT grant and stay bound to that exact ID after revocation.

Every grant (PAT, OAuth consent and CLI device approval) also names its tool groups: a required, non-empty, de-duplicated set of known groups (`read`, `edit`, `assets`, `export`, `pull_requests`, `index_admin`, `kb_admin`, `sealed`) stored in canonical order on `McpGrant.toolGroups`. Mint, consent and device approval validate the set; the web pickers offer the Read, Propose edits and Direct edits presets (new connections start on Read) and the groups themselves under Advanced. The grant verifier reads the groups with the same live grant row, and a row with an empty, unknown or non-canonical set is an inactive generation. Groups only ever narrow: every existing scope, KB-bit, live-identity and domain check still applies, and the group check is additional. A `tools/call` for a tool outside the connection's groups is `FORBIDDEN` before any domain call (`knowledge_bases_list` and `knowledge_bases_get` are supporting tools that need no group). The same demand travels with the principal into every domain authorization of that call, including the mutation barriers' lock-held rechecks, so removing a group while a publication waits on a lock denies it (an already `COMMITTING` publication may finish). Operation-level checks sit in the shared domain services: `knowledge_changes_apply` with `assetPut`/`assetRemove` (and asset imports) needs `assets`, and an upload needs `edit` for Markdown or `assets` for an asset, including writes and finishes of an already staged upload. Git fetch and bearer asset reads need `read`, Git push needs `edit`, and bearer export downloads need `export`. OAuth consent never holds `sealed`, because OAuth credentials never resolve sealed values. Browser sessions hold no grant and are unaffected.

The narrow exception is bearer PAT self-revocation at `POST /api/kb/token/revoke-self`: no body, a separate rate limit, and only the presented token/grant may be revoked. MCP, OAuth discovery, the MCP login/consent pages and PAT minting are always on; there is no availability flag. `/mcp` uses stateless JSON POST with the SDK's 2026-07-28 per-request metadata, the complete common kb/1 catalog, and no cookie authentication, sessions, legacy transport or subscriptions. Asset/export bearer reads use the same admission and recheck live authority before each frame; browser sessions remain a separate path. Shutdown closes bearer admission before draining work. Revocation prevents later reservations; a durable COMMITTING publication can still reconcile, and transmitted bytes cannot be recalled.

OAuth resource admission supports both Bearer and sender-bound DPoP access. DPoP proofs bind the actual method and operation path (including asset and export GETs) on the configured canonical origin. Provider and resource admission atomically reserve proofs in the durable verification table through verifier expiry plus 1s, so cleanup and server replacement cannot admit a still-valid replay; a lapsed marker may be renewed before cleanup, and freshness still governs admission. Git password credentials and self-revocation remain PAT-only. Invalid credentials return 401; JWKS or replay-storage service failures return a redacted 503. Owned admission and SQL recheck I/O has a 30-second budget; PostgreSQL transaction and idle deadlines bound authority-lock retention even when a reply is lost. Cancellation terminates only the owned backend, waits for server acknowledgement before forcing transport closure, and retains the I/O permit until cleanup drains; continuations inside an operation lease use that lease's query and deadline. Shutdown cancels owned I/O and joins it before releasing ownership. Forced-2FA tombstones are written atomically only after checking the complete live policy under the same authority transaction lock as policy and identity writers. Durable query principals retain credential bindings and preserve null PAT expiry as never expiring.

OAuth consent uses a signed Better Auth transaction, a session/client/nonce HMAC reference, and a durable ConsentIntent. Prepare validates the registered client, redirect, resource and scope ceiling; approve revalidates the live session, identity and KB bits under the authority transaction lock; a request for sealed recipients is rejected with the typed `SEALED_VALUES_REQUIRE_CLI_OR_PAT` error before any grant work, and review never offers any. Empty ACL is explicit. Approval and its random grant generation commit before code issuance. Replaying an approval cannot change its selection. Reuse is limited to subsets (scopes, tool groups, create capability and KB bits) and monotonically narrows the shared grant (older credentials lose removed rights); consent reuse only narrows. A person may widen or narrow an existing live grant in place through `mcpGrants.updateMine` (cookie session + live 2FA, never a token): same generation, every added KB bit validated against live bits exactly as at mint (rejected, never clipped); KB entries change only through an explicit per-KB patch, or a narrowing-only `aclCap` that limits every stored entry atomically (preset changes on ACLs of any size). The edit is applied under the authority lock so the next call and any work still waiting on the lock see it, and audited as `MCP_GRANT_WIDENED` / `MCP_GRANT_NARROWED` with before/after values. PAT scopes change on the grant and token snapshot together; OAuth scope changes still need re-consent, and OAuth grants cannot gain `sealed`. Foreign grants are not found; revoked or expired ones cannot be edited. Temporary access (`updateMine` with a duration of 1 hour, 1 day or 7 days) is a separate `McpGrantElevation` record that only adds groups, KB bits or creation (never scopes), validated exactly like a widening; at most 5 are in force per grant. Effective authority is the base grant united with every elevation that is not ended and whose `expiresAt` is after the database clock, read live by admission, discovery and every lock-held recheck, so expiry needs no sweeper and work still waiting on a lock is denied once it lapses. `mcpGrants.endElevationMine` ends one immediately, and any `updateMine` that narrows the base grant (or OAuth consent reuse that narrows it) ends every active elevation of that grant in the same transaction, so a narrowing is never masked by temporary access. Creation is audited as `MCP_GRANT_ELEVATED` and every early end as `MCP_GRANT_ELEVATION_ENDED`; natural expiry needs no event. Elevations are authority records and are never deleted. A KB created during temporary access keeps its creator bits on the base grant. Intents and grant tombstones survive provider artifact cleanup and account removal. Refresh claims require the exact approved generation, live identity, unexpired provider refresh row and subset scopes. Access TTL is 10m, refresh slides 72h, provider retry cache is 30s; cached pairs still need live admission. DPoP replay storage must retain reservations through verifier expiry plus 1s. The installed provider issues authorization codes only after these procedures durably approve the intent; the procedures themselves do not issue codes. Provider hooks check the approved generation before code/refresh issuance. MCP accepts sender-bound OAuth credentials with the DPoP scheme and proof header; PATs use Bearer only. Both provider and resource verification reserve proofs durably through the final accepted second and recheck freshness after blocking storage work, so expired-row cleanup cannot reopen an in-flight proof. The canonical resource and attachment origin comes from BETTER_AUTH_URL; PUBLIC_APP_URL is optional translation metadata only. The library’s delete-consent, update-consent and token revoke endpoints reject mutations before effects, and discovery does not advertise library revocation. Users revoke durable generations through mcpGrants.revokeMine; new scope selections use signed consent.

Device start (`POST /api/auth/device/code`, client_id `kb-cli`) is public with a separate fail-closed IP budget and returns snake_case fields, a 256-bit secret and a 10-minute expiry. Only the digest is stored. Optional public `cliCredentials.registerDeviceRecipient` accepts the device secret and an exact X25519 public key/UUID before any human claim, with its own fail-closed IP budget. Same-key retries are allowed only before claim; key replacement and post-claim registration are rejected. The CLI reads its private key from an existing owner-only host file and never uploads it. Human cookie-session GET `/api/auth/device?user_code=...` claims the code and returns a session-bound nonce and the registered public recipient descriptor. `cliCredentials.selectDeviceIntent` persists one exact selection, including an explicitly empty ACL, optional expiry, create bits and exact sealed recipients (none by default). POST `/api/auth/device/approve` or `/deny` sends `{userCode}` plus `x-device-approval-nonce` and a trusted Origin; both the pre-plugin gate and provider hooks enforce claim/session/live 2FA/nonce. All human device operations and Better Auth session revocations share the committing authority lock: completed revocation denies subsequent operations; an already committed approval remains exchangeable after logout. Denial requires a claim but no selection. A PAT never approves a device. All selected sealed recipients must match that registered descriptor at selection, approval and exchange; they additionally require live owner rights, enrolled 2FA and exact record/expiry validation. Built-in `/device/token` cannot issue a browser session.

Public POST `/rpc/cliCredentials/exchangeDeviceCode` accepts only `{json:{deviceCode,name}}`; its success is `{json:{credentialId,userId,secret,expiresAt,resource}}`. Typed HTTP400 errors carry `json.data.error` (`authorization_pending`, `slow_down`, `access_denied`, `expired_token`, `invalid_grant`). Device and human PAT display names are trimmed Unicode text of 1–120 characters; C0, DEL and C1 controls (including tab/CR/LF) are rejected before trimming or persistence. Invalid names return HTTP400 and leave approval usable for a valid retry. Pending polls commit their timestamp without consuming approval. The authority/device/user locks enclose live-rights revalidation, the shared PAT mint (10 active, default90/max365 days), exact recipient grants, consumption and plugin-row removal in one transaction. Permission loss rejects the whole approval. Consumed retries never return a secret; a lost successful response requires a fresh login. Device bearer knowledge is only exchange authority, never general oRPC authority. The browser starts with no KB/create/recipient choices, and tool groups on the Read preset. Exact sealed references are entered individually, with an explicit unchecked confirmation and expiry. Lost decision replies immediately show uncertainty; combined unavailable codes do not rule out an existing PAT, and link to Settings token revocation.

The admin panel and API rank model/tier options by measured retrieval quality (Gemma first, then 1K, 2K, 4K, 8K), recommend the first option below the 90% boundary of the detected worker limit, and identify smaller-memory alternatives. A model identity switch serves lexical results with `EMBEDDING_MODEL_CHANGED` notices until each attached KB is rebuilt. The worker periodically removes only obsolete registry weight files with no remaining index-generation references, retaining selected and pending artifacts. The built-in provider kind is `SYSTEM_BUILTIN`; the active model id and context tier are reported separately.

## Optional asset authority

Disk CAS remains the default. Opt-in S3 makes remote objects authoritative and
local asset payload a strictly bounded shared cache; staging/ZIPs still need
local disk capacity. Logical lineage quotas and live read/revision/manifest/KB
authority checks stay unchanged. Downloads remain server-streamed and private;
there is no signed public bypass or remote deletion. See the
[operator role/configuration matrix](./assets.md#opt-in-s3-operation-and-role-configuration)
for writer/operator/dump identity separation, advisory recency, outage behavior,
dual-fenced initialization/migration/reconciliation and reference-only backup
retention. One server and one worker still share one host/local volume.
