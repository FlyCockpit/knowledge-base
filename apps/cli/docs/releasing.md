# Releasing

Releases are automated by the root `Release` GitHub Actions workflow
(`.github/workflows/release.yml`) and
[`dist`](https://opensource.axo.dev/cargo-dist/) (cargo-dist). You bump the CLI
version, merge it to the default branch, then manually run the workflow with
that version tag. CI builds every platform, generates installers + checksums,
and publishes a GitHub Release.

## What gets built

From `dist-workspace.toml`:

| Platform | Target triple |
|----------|---------------|
| Linux x86_64 (static) | `x86_64-unknown-linux-musl` |
| Linux ARM64 (static) | `aarch64-unknown-linux-musl` |
| macOS Intel | `x86_64-apple-darwin` |
| macOS Apple Silicon | `aarch64-apple-darwin` |
| Windows x64 | `x86_64-pc-windows-msvc` |

The Linux legs run `dist build` inside `apps/cli/ci/musl-builder.Dockerfile`
(Rust's Alpine image pinned by multi-arch digest; Alpine's gcc/g++ provide
`libgomp.a` and `libstdc++.a`) on `ubuntu-latest` and `ubuntu-24.04-arm`. The
job fails unless each binary has no ELF interpreter, no `NEEDED` entries and
libgomp linked in, and writes the toolchain package versions to the job
summary. `kb-model-smoke.yml` runs the real-model parity lane against the same
static binaries. To reproduce locally (x86_64):

```sh
docker build -f apps/cli/ci/musl-builder.Dockerfile -t kb-musl-builder apps/cli/ci
docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp -e CARGO_HOME=/tmp/cargo \
  -v "$PWD:/src" -w /src/apps/cli kb-musl-builder \
  cargo build --locked --profile dist -p kb --target x86_64-unknown-linux-musl
readelf -lW apps/cli/target/x86_64-unknown-linux-musl/dist/kb | grep INTERP  # expect nothing
```

Installers generated: **shell** (`curl … | sh`) and **PowerShell**
(`irm … | iex`), attached to the release as artifacts. Archives also include
`LICENSE`, `NOTICE`, and `THIRD-PARTY-LICENSES.md` from the repository root,
alongside the CLI’s existing `LICENSE-APACHE`. The release also contains
`sha256.sum` and `THIRD_PARTY_LICENSES.html`, generated by cargo-about from
`apps/cli/about.toml` and `apps/cli/about.hbs`.

## Cutting a release

```sh
# 1. Bump the version in apps/cli/Cargo.toml (1.0.0 for the first public release).
# 2. Merge that change to the default branch.
# 3. In GitHub Actions, run the root "Release" workflow from the default
#    branch with: version = v1.0.0
```

The workflow validates that it is running from the default branch and that the
requested `vX.Y.Z` tag matches `apps/cli/Cargo.toml`, runs the release
preflight gates, creates the GitHub Release for that tag, and uploads the CLI
artifacts. Watch it in the repo's Actions tab; when it's green, the GitHub
Release has all the artifacts.

## One-time setup

1. **Repo must be public** for installer downloads to work without auth tokens.
2. **Optional local cargo-dist:** CI downloads the pinned cargo-dist 0.34.0
   archive and verifies its pinned SHA-256 before installing it. Normal release
   cutting does not require it locally. To inspect release plans locally:

   ```sh
   cargo install cargo-dist --version 0.34.0 --locked
   dist plan
   ```

## Changing release behavior

The root `.github/workflows/release.yml` owns release orchestration and is
hand-maintained — do not overwrite it with `dist generate` output. Cargo-dist
artifact behavior (targets and installers) still comes from
`dist-workspace.toml` here. When you change artifact targets or installers,
edit `dist-workspace.toml`, install `cargo-dist` if needed, then inspect the
generated output before porting the relevant changes into the root workflow:

```sh
cargo install cargo-dist --version 0.34.0 --locked
dist init      # interactive; or
dist generate  # emit a reference release.yml from the config
```

CI has no "release drift" check, so review cargo-dist workflow changes
deliberately whenever you change `dist-workspace.toml`.

## Optional: crates.io and cargo-binstall

Not enabled by default. To also publish to crates.io so `cargo install` /
`cargo binstall` work:

1. Add a `CARGO_REGISTRY_TOKEN` secret.
2. Add `"cargo:"` to a publish step (see dist docs on `publish-jobs`), or run
   `cargo publish` in a small added job. `dist`'s artifacts already carry the
   metadata `cargo binstall` needs.
